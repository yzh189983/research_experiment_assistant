### 16. 自动化测试从 0 到 1 + CI　✅ 已完成（2026-11-18）

> **实现**：新增 `tests/_env.py`（临时 data 目录隔离，绝不碰真实数据）、`tests/conftest.py`（pytest 兼容）、5 个测试文件覆盖 crypto / verify / db / report / api，**35 项测试全部通过**。`pyproject.toml` 加 `[tool.pytest.ini_options]` 与 coverage 配置；`python -m unittest discover -s tests` 零依赖即可运行。

- **现状**：`tests/` 只有 3 个手动脚本（`e2e_test.py`、`terminal_test.py`、`fake_ssh_server.py`），需要先手工起服务才能跑；没有 `pytest/unittest` 断言，没有 CI 配置。
- **问题 / 机会**：第 1 版 33 项测试结果良好，但都是一次性验证、无法回归。核心逻辑（`verify.py` 数字回查、`crypto.py` 加解密、`db.py` 迁移、`gitlineage.py` 快照）改动后没有任何自动保护，尤其判据核验出错会直接污染论文结论。
- **建议做法**：
  - 引入 `pytest`，按层建测试：`test_db.py`（schema 迁移、隔离、事务）、`test_verify.py`（数字回查/判据判定边界）、`test_crypto.py`（加解密与脱敏）、`test_report.py`（导出内容完整）、`test_api.py`（Flask test_client 覆盖鉴权与越权 11 条）。
  - 用 `conftest.py` 提供临时 `DATA_DIR` fixture，避免测试污染真实 `data/`。
  - 加 GitHub Actions：push/PR 跑 `pytest` + `ruff`/`flake8`；`e2e` 用 fake SSH server 做可选 job。
  - 覆盖率门槛先设 40%，重点模块（verify/crypto/db）单列 70%。
- **预期收益**：改动不再靠"手动点一遍"，是后续重构（第 17、19 项）的安全网。
- **参考竞品 / 依据**：`tests/` 目录现状；对比第 1 版 P0 验证方式（33 项手工断言）的可重复性缺口。

### 17. 事件持久化与运行中任务可恢复　✅ 已完成（2026-11-18）

> **实现**：新增 `stream_events` 表作为事件 journal，每条 SSE 事件既进内存队列（低延迟）也落库（拿全局自增 id）。`api_stream` 支持 `Last-Event-ID`：浏览器断线重连后从 DB 补发事件并对去重，重启也不丢。`runs` 加 `heartbeat_at`，监控每轮写心跳；`bootstrap()` 按退出码/进程存活恢复或判失联，并新增 `_reap_stale_runs` 每 30 秒巡检僵尸任务（心跳超时但线程已死时重挂或标记 lost）；SSE 结束自动裁剪事件日志（保留 2000 条）。

- **现状**：`bus.py` 用进程内 `dict + queue.Queue`（`BUF_MAX=300`），只有显式 `db.add_event` 的事件落库；日志与 metric 只在内存 buffer。监控是每 run 一个 daemon 线程，`_running` 不持久化。
- **问题 / 机会**：**服务一重启，正在跑的实验状态永远卡在 `running`**，内存事件全部丢失，刷新页面拿不到历史日志。README 声称"重启自动接管"，但 `_running` 无持久化时这条链是断的。多人/多 worker 部署时，SSE 也收不到其他 worker 的事件。
- **建议做法**：
  - 日志与指标全量落 `events` / 新 `run_logs` 表，内存只做热缓存；SSE 断线重连后按 `last_event_id` 从 DB 补发。
  - `runs` 增加 `heartbeat_at`、`monitor_pid`；启动时把"running 但心跳超时"的 run 重新挂上监控线程，或明确标记 `lost` 并通知。
  - 事件总线抽象成接口，默认 `MemoryBus`，预留 `RedisBus` / `DBBus`，多 worker 时可切换。
  - SSE 加 `Last-Event-ID` 支持与游标分页，避免重放全量。
- **预期收益**：真正实现"重启不丢实验"，也是从个人工具走向可部署服务的关键一步。
- **参考竞品 / 依据**：`core/bus.py` L1–47、`core/monitor.py` L17–40、`app.py` SSE L1206–1229。

### 18. 依赖清单与配置工程规范　✅ 已完成（2026-11-18）

> **实现**：`pyproject.toml` 补全为与 `requirements.txt` 一致的 8 个依赖，并加 `dev`（pytest）可选依赖组、pytest/coverage 配置；新增 `.gitignore`（忽略 `data/`、密钥、缓存、日志，防止凭据误提交）；新增 `config.example.json` 脱敏示例。`rekit doctor` 现在会检查所有运行依赖，支持 `--fix` 一键补装并提示重启。

- **现状**：`requirements.txt` 列 8 个包，`pyproject.toml` 只列 3 个（缺 `flask-sock`、`cryptography`、`python-docx`、`pypdf`、`simple-websocket`）；全部 `>=` 无上界、无 lock；无 `.gitignore`、无 `config.example`。
- **问题 / 机会**：`pip install .` 会缺依赖导致启动失败；`data/` 含 `app.db`、`secret.key`、主机密码密文，一旦误提交 `git add .` 就是安全事故。
- **建议做法**：
  - 统一为单一事实来源：`pyproject.toml` 补全 dependencies，`requirements.txt` 用 `pip-compile` 生成带 hash 的 lock。
  - 补 `.gitignore`：`data/`、`__pycache__/`、`*.log`、`.venv/`、`data/certs/`。
  - 提供 `config.example.json`（脱敏占位）与 ` doctor --fix` 的缺失依赖一键安装建议。
  - 固定 Python 版本下限（当前 `>=3.9`），在 CI 里跑 3.9 / 3.11 / 3.12 矩阵。
- **预期收益**：新用户 `pip install` 一次成功；避免凭据误入版本库。
- **参考竞品 / 依据**：`requirements.txt` L1–8、`pyproject.toml` L10–14、`config.py` DEFAULTS。

### 19. app.py 按 Blueprint 拆分　✅ 已完成（2026-11-18）

> **实现**：新增 `web/blueprints.py` 定义 `api_bp`，把 **54 个 `/api/*` 路由**全部从 `@app.*` 迁到 `@api_bp.*`，在 app.py 末尾统一 `register_blueprint`。前端全部用固定 URL 调用 API、不依赖 Flask endpoint 名，迁移零行为变化（35 项测试全通过）。页面路由（12 个，含 `url_for` 引用）、全局钩子与 WebSocket 保留在 app.py，避免 endpoint 命名连锁改动。后台任务与 SSE 生成器仍在 app.py，作为后续可继续细拆的空间。

- **现状**：`app.py` 约 1730 行、67.9 KB、**67 个路由**，覆盖 auth / 实验 / runs / 主机 / 终端 / 用户 / 设置 / 报告 / batch / usage，还混入 `bg()` 后台调度、SSE 生成器、SSH 进程扫描。
- **问题 / 机会**：单体文件让定位与测试成本越来越高；第 16 项的 API 测试、第 17 项的总线改造都要在这一个文件里动刀，冲突风险大。
- **建议做法**：按域拆 `routes/` 包：`auth.py`、`experiments.py`、`runs.py`、`hosts.py`、`terminal.py`、`reports.py`、`settings.py`、`usage.py`；`app.py` 只留 app 工厂、`before_request`、错误处理和注册 Blueprint。后台任务挪到 `core/jobs.py`。
- **预期收益**：为后续所有改造降低耦合；每个 Blueprint 可独立测试。
- **参考竞品 / 依据**：`app.py` L170–193（`bg()`）、L1206–1229（SSE）、67 处 `@app.*route`。

## P1 · 科研能力纵深

> 这一组是把"能跑完实验"升级为"能得出可信、可发表的结果"。与第 1 版的核验/判据一脉相承，往统计严谨性和 AI 自审继续走。

### 20. 多次运行的统计汇总与显著性检验　✅ 已完成（2026-11-19）

- **现状**：`metrics_stats` 只有单次 run 的首值/末值/最优/变化率；批量实验对比展示各组的最后值。
- **问题 / 机会**：科研结论几乎不能靠单次 run。用户现在只能自己导出数字到 Excel 做均值/方差和 t 检验，工具"最后一公里"没走完。
- **建议做法**：
  - 对同一实验/同一参数组的多 run 计算 mean ± std、置信区间、以及配对 t 检验 / Wilcoxon（给出 p 值）。
  - 在「批量实验对比」表增加"均值 ± 标准差"列和"显著性"标注，点开可见分布箱线图。
  - 报告自动加"统计方法"小节，写明 n、检验方法与 p 值，并提示"样本量不足"时谨慎下结论。
  - 判据支持统计型：`mean(metric) >= x`、`p < 0.05`。
- **预期收益**：从"能跑实验"跨到"能支撑论文 Results"，这是科研用户愿意长期留下的核心理由。
- **参考竞品 / 依据**：Sakana AI Scientist（多 seed 汇总）、Weights & Biases（runs 对比 + 误差带）；现状见 `core/summarizer.py` 的 `_stats()`。
- **落地记录（2026-11-19）**：新增 `core/stats.py`：多 run `mean ± std` / 95% CI / n，Welch t 检验与 Mann-Whitney U（纯标准库近似，含并列校正）；`batch compare` 每行带多 run 统计，实验页指标表加「多 run 均值±std」列，报告 Markdown 加「多 run 统计汇总」段。`GET /api/experiments/<id>/stats` + `POST /api/stats/compare` 提供 API。样本量不足时明确提示谨慎解读。

### 21. AI 自审 / 模拟同行评审　✅ 已完成（2026-11-19）

- **现状**：已有结果核验（数字回查指标）与判据判定，但没有对"结论是否站得住"的整体审视。
- **问题 / 机会**：AI Scientist 用自动审稿给论文打分并指出漏洞；用户写完报告后最需要的是"有没有漏洞、还差什么实验"，而不是再生成一段总结。
- **建议做法**：
  - 报告生成后追加一轮"审稿人"LLM 调用，按维度打分：假设是否闭合、基线是否充分、消融是否完整、指标是否合适、是否有混淆因素、结论是否过度。
  - 输出"主要问题 / 次要问题 / 需要补的实验"，并可一键把这些建议变成新的 follow-up 实验（复用模板与批量创建）。
  - 审稿意见写入审计与报告附录，明确标注"AI 生成，需人工判断"。
- **预期收益**：把工具从"写报告"推进到"改进实验"的闭环，契合人在环理念。
- **参考竞品 / 依据**：Sakana AI Scientist（自动 reviewer）、Google Co-Scientist（self-review）；与已实现 `core/verify.py` 天然衔接。
- **落地记录（2026-11-19）**：新增 `core/review.py`：总结生成后自动追加一次「审稿人」LLM 调用，按 6 个维度打分（假设闭合/基线/消融/指标/混淆/结论），输出主要问题、次要问题、待补实验与总体意见；标「AI 生成，需人工判断」，写入 `runs.review_json` 与审计。实验页「AI 自审」按钮可手动重审，报告附录也含审稿结果。审稿失败不影响主结论。

### 22. 失败自动诊断与修复建议　✅ 已完成（2026-11-19）

- **现状**：run 失败时只有日志尾部与退出码，用户要自己翻 SSH 日志判断是 OOM、CUDA、依赖缺失还是数据路径错。
- **问题 / 机会**：失败很常见（尤其 GPU 机器），诊断占掉大量时间；错误模式高度可复用。
- **建议做法**：
  - 建错误签名库：`CUDA out of memory`、`ModuleNotFoundError`、`Connection refused`、`No such file`、`exit 137`（OOM kill）等，映射到原因与建议动作。
  - 失败时自动生成诊断卡：命中签名、关键日志行（引用行号）、建议（降 batch / 装依赖 / 检查路径）。
  - 高置信度签名支持"一键修复重跑"：改代码参数或补依赖后重新入队（复用第 11 项断点续跑）。
  - 诊断结果做匿名统计，看哪类失败最常见，反过来优化生成代码的 Prompt 约束。
- **预期收益**：显著降低"看日志猜原因"的时间，也提升无人值守的可靠性。
- **参考竞品 / 依据**：`core/monitor.py` 的失败判定、`core/ssh_runner.py` 的日志尾部采集。
- **落地记录（2026-11-19）**：新增 `core/diagnose.py` 错误签名库（CUDA OOM / ModuleNotFoundError / exit 137 / Connection refused / 路径不存在 / KeyError / 语法错误等 12 类），失败时从日志尾部+退出码命中签名，生成含证据行号与修复建议的诊断卡，写入 `runs.diagnosis_json` 并发事件；实验页日志区上方显示诊断卡。`GET/POST /api/runs/<id>/diagnosis` 可查看与重新诊断。匿名统计与一键修复重跑留待后续。

### 23. LLM 调用可靠性：重试 / 流式 / 多模型 fallback　✅ 已完成（2026-11-19）

- **现状**：`stream=False` 硬编码；网络异常 / 429 / 5xx 直接抛 `LLMError`；只用配置里单一 model；`extract_json` 失败直接报错，不会把错误回喂模型。
- **问题 / 机会**：长方案生成 240s 超时后整个阶段重来；第三方 API 偶发 429 会中断实验链路。
- **建议做法**：
  - 指数退避重试（429/5xx/超时，最多 3 次）＋ 可配 `fallback_models` 列表，主模型失败自动切备用。
  - 流式输出方案/代码生成，前端逐字显示；超时可续，不再"转圈到失败"。
  - JSON 解析失败时把"解析错误 + 原始输出"回喂模型让其自修（1 次），仍失败再走规则兜底。
  - 调用级熔断与预算联动：连续失败 N 次暂停并告警，避免烧 token。
- **预期收益**：链路不再被第三方 API 抖动打断，长任务体验明显改善。
- **参考竞品 / 依据**：`core/llm.py` L32–82、L85–129。
- **落地记录（2026-11-19）**：重写 `core/llm.py` 的 `chat()`：指数退避重试（429/5xx/超时，最多 3 次）、`fallback_models` 自动切换、SSE 流式输出（`stream` + `on_delta` 回调）、连续失败熔断（可配阈值，60s 冷却）；`chat_json()` 解析失败把错误+原始输出回喂模型自修一次。config 的 `llm` 段新增对应开关，设置页可配置。

### 24. SFTP 断点续传与 SSH 连接复用　✅ 已完成（2026-11-19）

- **现状**：`sftp.put()` 全量覆盖；监控每 tick（约 3s）重新 `connect + SFTP + close`；`connect()/run()` 无指数退避；`_poll_until` 有 3600s 硬超时。
- **问题 / 机会**：代码/数据文件大时，断网重传从头来；高频重连在跳板机/AutoDL 上容易触发限流。
- **建议做法**：
  - 大文件用 `sftp.put(..., callback=...)` + `.part` 临时文件 + 大小/校验和比对，支持 resume。
  - 监控连接用 ControlMaster（`ControlPath` 复用 socket）或长连接 + keepalive，减少每轮握手。
  - 连接失败加指数退避与抖动，区分"认证失败"（不重试）与"网络抖动"（重试）。
  - 长任务硬超时可配，并允许对"仍在产出日志"的任务自动续期。
- **预期收益**：弱网/大文件场景不再失败，远程交互负担下降。
- **参考竞品 / 依据**：`core/ssh_runner.py` L223、L322–331；`core/monitor.py` L69–98。
- **落地记录（2026-11-19）**：`core/ssh_runner.py`：`connect_with_retry()` 指数退避（认证失败不重试）、`get_cached_client()` 按主机缓存连接 + keepalive 30s + 失效重建、`upload_file()` 用 `.part` 临时文件按大小断点续传并跳过未变更文件；`monitor.py` 的监控 tick 与 `_drain` 改用缓存连接，异常时 `drop_cached_client()`，不再每 3 秒握手。长任务硬超时可配置留待后续。

## P1 · 团队协作与分享

> 当前只读观察链接已能"给别人看"，但还缺"多人一起做"的组织能力。

### 25. 项目 / 工作区概念与细粒度角色　✅ 已完成（2026-11-20）

- **现状**：数据以"用户"为隔离边界，实验是扁平列表，没有"项目"或"课题组"层级。
- **问题 / 机会**：同一个用户做多个课题时实验混在一起；团队共用时要么共享账号（不安全），要么完全隔离（无法协作）。
- **建议做法**：
  - 引入 `projects` 表：实验归属项目，项目有成员与角色（owner / editor / viewer）。

### 35. 实验代码一键推送到个人 GitHub 仓库（Git 谱系闭环）　✅ 已完成（2026-11-19）

- **现状**：`core/gitlineage.py` 已把每个实验目录 `data/workspace/exp_<id>` 做成独立 git 仓库，`commit_snapshot / history / diff / files_at / code_at / restore / clone_for_fork` 一应俱全，每次 run 前锁定 commit 写入 `runs.git_sha`；`core/crypto.py` 已有 `encrypt / decrypt`（Fernet）；`users.profile_json` 里有 `github` 字段，但目前只是展示用的链接。整条 Git 谱系**止于本地**，没有 remote、没有 push。
- **问题 / 机会**：报告里的 `git_sha` 现在只是一串字符，点不开、换机器看不到、分享给导师要手工打包。这恰好卡在「可复现实验」这条主线的最后一公里：谱系已经能锁定代码版本，但没法把它推到一个稳定、可访问、可引用的地方。做成之后，`git_sha` 直接变成 GitHub commit 链接，报告 → 代码 → 运行结果形成闭环。
- **建议做法**：核心不是「实现 Git」，而是「给现有 Git 加 remote 并 push」——凭据按用户加密、仓库按实验一个、推送手动触发、报告带链接。具体拆解见下方实现清单。
- **预期收益**：以很小的技术风险，补齐「结果核验 + Git 谱系 + 可复现」这条差异化主线的最后一环；用户换机、长期存档、投稿引用代码版本都变得自然。
- **参考竞品 / 依据**：现有 `core/gitlineage.py`（170 行，本地 git 全能力）、`core/crypto.py` 的 `encrypt / decrypt`、`core/db.py` 的 `runs.git_sha`、`templates/profile.html` 的 `pf-github` 字段。竞品中 W&B / ClearML 走云端托管，本项目的差异是**本地优先、代码在自己账号下**。

> **落地记录（2026-11-19）**：阶段 1（MVP）已完成，即下方清单 A–G。新增 `core/github.py`（API 校验 Token 与写权限）、`git_remotes` 表、`runs.remote_url/remote_sha` 字段、5 个 API 路由、设置页与实验页 UI、四类页面的 commit 链接，以及 `tests/test_github_push.py` 6 项测试（全套 41 项通过）。推送用一次性 URL，Token 不写 `.git/config`；直接用 HEAD 指向的快照推送。阶段 2/3（自动推送、自动建仓、Actions 联动）暂不实现。

#### 35.1 实现清单（按文件 / 模块拆解）

**A. 数据层 `core/db.py`**
- 新增表 `git_remotes`：`id / user_id / provider / repo_full_name / token_enc / token_hint / default_branch / created_at / updated_at`。Token 只存 `crypto.encrypt()` 后的密文；`token_hint`（尾 4 位）用于前端展示，明文永不回传。
- `runs` 表加两列：`remote_url TEXT DEFAULT ''`、`remote_sha TEXT DEFAULT ''`，记录推送成功后的仓库地址与远程 commit SHA。
- 照 `core/db.py` 现有的 `ensure_columns()` 追加列模式做迁移，不改旧数据。

**B. Git 层 `core/gitlineage.py`**
- `_git_raw()` 增强：支持注入 `GIT_TERMINAL_PROMPT=0`、`credential.helper=`（禁用系统凭据助手），超时默认 30s。
- 新增 `set_remote(eid, url)` / `remove_remote(eid)`：只写该实验自己的 `.git/config`，用一次性带 token 的 URL，**不要把 token 写进 `.git/config`**（避免明文落盘）。
- 新增 `push_snapshot(eid, repo_full_name, token, branch='main')`：以 `HEAD:refs/heads/<branch>` 推送；捕获 stderr 并用 `crypto.redact()` 脱敏后返回；成功返回本地 `rev-parse HEAD`。
- 新增 `scan_sensitive(files)`：推送前检测 `sk-`、`api_key`、`password`、`Bearer `、内网 IP / 绝对路径等，返回警告列表供 UI 确认。
- 复用现有 `_sha / ensure_repo / history`；`code_at()` 已能从 commit 还原代码，可与远程链接共用。

**C. 凭据与校验 `core/crypto.py` + 可选 `core/github.py`**
- 复用 `encrypt / decrypt` 按 `user_id` 隔离存放 Token，禁止放进全局 `data/config.json`。
- 引导用户用 **fine-grained PAT，只给选定仓库 Contents: read+write**（就是本项目推送时踩过 403 坑的原因）。
- 保存前先校验：调 `GET /user` 与 `GET /repos/{owner}/{repo}` 确认账号与 push 权限，避免推送时才发现无权限。

**D. 后端 API（归入 `web.api_bp`）**
- `GET /api/git/github/configs`：列出当前用户的仓库配置（不含 token）。
- `POST /api/git/github/configs`：保存/更新 Token + 默认仓库（先做 C 中校验）。
- `DELETE /api/git/github/configs/<id>`。
- `POST /api/git/github/test`：测试连接与写权限，返回账号名、仓库、权限结论。
- `POST /api/experiment/<id>/push`：body 含 `repo_full_name / branch / privacy`，执行 B 中推送；成功后写 `runs.remote_url / remote_sha`，并写 `audit_log`。建议短超时同步或复用 `core/bus.py` 做异步 + 状态事件，避免 UI 卡死。
- `GET /api/experiment/<id>/push/status`：异步模式下查询推送结果（可选）。

**E. 前端**
- 设置页新增「GitHub 集成」区块：Token（密码框）、默认仓库、测试连接按钮、已配置列表。
- 实验页 Git 谱系面板：每个 commit 旁加「推送到 GitHub」按钮 + 目标仓库下拉；推送后显示远程 commit 链接。
- 报告导出（`core/report.py` 及 Markdown / Word / 打印页三处）：把 `git_sha` 渲染为 `https://github.com/<repo>/commit/<sha>` 可点击链接。
- 推送前弹出 `scan_sensitive` 的扫描结果与二次确认；默认勾选「私有仓库」。

**F. 审计与错误**
- `audit_log` 记录 `git_push` 动作：谁、实验、commit、目标仓库、结果、时间。
- 错误分类提示：凭据无效 / 无写权限（403）/ 仓库不存在 / 网络超时，且 token 不得进日志。

**G. 测试**
- `tests/test_gitlineage.py` 扩展：用本地裸仓库（`file://` remote）mock 推送，不依赖网络，验证 `push_snapshot / set_remote / remove_remote`。
- Token 加密往返、`scan_sensitive` 命中、API 越权（A 用户不能用 B 的 Token）三类单测。

#### 35.2 分阶段落地

| 阶段 | 范围 | 说明 |
|---|---|---|
| 阶段 1（MVP） | A + B + C + D 核心 + E 设置页/按钮 + F + G | 手动推送、加密 Token、私有仓库默认、报告带链接 |
| 阶段 2 | E 敏感扫描确认强化、`scan_sensitive` 规则库、批量/自动推送、多 remote | 需真实用户反馈后再投入 |
| 阶段 3 | GitHub API 自动建仓、GitHub Actions 联动、PR 工作流 | 与「开放 API / 插件化（33）」协同 |

#### 35.3 风险与边界

- **网络**：本机实测连 GitHub 443 反复超时，推送必须异步 + 可重试 + 明确状态反馈，不能同步阻塞 UI。
- **权限**：fine-grained Token 最小权限；按用户隔离；绝不因开了集成而绕过多用户隔离。
- **泄露**：代码可能硬编码数据路径 / API Key / 服务器 IP；默认私有仓库 + 推送前扫描 + 日志脱敏三重防护。
- **触发方式**：第一版只做手动推送。自动推送在凭据失效或网络不通时会静默失败，反成隐患。
