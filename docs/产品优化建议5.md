## AI 能力基线盘点

当前系统已经具备以下 AI 相关能力：

| 能力 | 当前形态 |
|---|---|
| 方案生成 | 从创新点生成研究假设、方法、数据集、基线与指标 |
| 代码生成 | 按方案生成 Python 实验代码，支持重写与快照 |
| 自动总结 | 聚合指标与日志，输出结论、局限、下一步与论文式表述 |
| AI 自审 | 六维模拟同行评审，打分并给出问题与补实验建议 |
| 失败诊断 | 错误签名匹配日志与退出码，输出修复建议 |
| LLM 可靠性 | 重试、fallback、流式、熔断、JSON 自修 |
| 成本账本 | 记录每次调用的 token、模型与用途 |

这些能力解决的是“AI 能不能帮我把实验跑起来”。第三版要解决的是：

- AI 说的每句话**有没有证据**
- AI 能不能记住**跨实验、跨项目的上下文**
- AI 能不能安全地**调用工具并执行操作**
- AI 生成的功能本身**如何评测和防止退化**
- AI 能不能从“执行者”升级为“科研合作者”

## P0 · AI 可信与安全底线

> 这一组不是花哨功能，而是后面所有 AI 能力的地基。没有证据绑定、评测集和工具边界，AI 越强，风险越大。

### 36. AI 输出可信分级与证据绑定　✅ 已完成（2026-11-20）

- **现状**：方案、总结、审稿、诊断都来自 LLM，界面上虽有数值核验和审计日志，但 AI 的自然语言结论没有统一的“可信度标签”。
- **问题 / 机会**：用户很难区分“实测数据支持”“日志证据支持”“模型推断”“常识性建议”。论文写作或组会汇报时，把推断当结论会带来科研风险。
- **建议做法**：
  - 所有 AI 输出统一标记来源类型：`实测`、`日志证据`、`推断`、`外部知识`、`待验证`。
  - 每句话可展开右下角证据：关联 `metric_name + step`、日志行号、代码 commit、报告段落。
  - 高风险字段（结论、显著性、论文表述）必须绑定证据；无证据时自动降级为“假设/建议”。
  - 在报告导出中附「AI 证据表」，与「结果核验」区分：核验查数字是否存在，证据表说明结论依据是什么。
- **预期收益**：AI 从“看起来很会写”变成“每句话都能追溯”。
- **验收口径**：随机抽 20 条 AI 结论，能定位到具体 metric/log/commit；无证据结论在 UI 和报告中明确标注。
- **落地记录（2026-11-20）**：新增 `core/ai_trust.py` 与 `ai_outputs` 表，方案/代码/总结/审稿/诊断生成时自动登记五档可信级别（实测支持 / 日志代码支持 / 推断 / 外部知识 / 待验证）、逐句分级与证据摘要；实验页新增「AI 可信」缩略卡，Markdown/Word/PDF 报告附可信分级段。

### 37. AI 功能评测集与回归看板　✅ 已完成（2026-11-20）

- **现状**：AI 相关功能靠人工点几个例子验证；LLM 输出随机，模型或 prompt 一改就可能退化。
- **问题 / 机会**：没有 golden set 就无法回答“新模型是不是更好”“这次 prompt 改动有没有伤害结论质量”。
- **建议做法**：
  - 建立 5 类评测集：创新点抽取、方案生成、代码补丁、总结结论、失败诊断。
  - 每类准备 20–50 个脱敏样本，给出参考输出、必含字段、禁止行为和评分 rubric。
  - 用「模型裁判 + 规则校验 + 人工抽检」三层评分；结果写入 `ai_eval_runs`。
  - 设置页或管理页增加 AI 回归看板，展示每个模型/prompt 版本的质量、延迟、成本和失败率。
- **预期收益**：AI 功能可以被版本化和回归，不再靠感觉调 prompt。
- **验收口径**：每次改 prompt/模型后一键跑评测，输出对比报告；核心任务通过率不低于基线。
- **落地记录（2026-11-20）**：新增 `core/ai_eval.py`、`ai_eval_cases` / `ai_eval_runs` 表与 5 个内置 golden cases（CUDA OOM 诊断、缺依赖诊断、未核数字、推断语气识别、API Key 脱敏）。设置页新增「AI 评测与回归」卡片，一键运行 `local-rules-v1` 回归并查看历史通过率；当前基线 5/5 通过。

### 38. AI 工具调用安全沙箱　✅ 已完成（2026-11-20）

- **现状**：AI 目前只产出文本/代码，由人确认后再执行；未来的文献检索、代码修复、跨实验查询都需要工具调用。
- **问题 / 机会**：一旦让模型直接调用数据库、文件系统、SSH、Git 或 Web，越权和误操作风险会迅速放大。
- **建议做法**：
  - 定义只读工具白名单：查询实验、查指标、查日志、查项目成员、查报告。
  - 写操作必须经过二次确认：创建分支、生成补丁、移动实验、重新运行、推送仓库。
  - 所有工具调用写入审计：调用者、参数、结果摘要、耗时、是否脱敏。
  - 敏感工具禁止直接暴露给访客分享链接和 `viewer` 角色。
  - 工具输出统一截断与脱敏，避免把 API Key、SSH 密码、个人路径带回模型上下文。
- **预期收益**：为“AI 代理”留出扩展空间，同时不牺牲安全和项目角色隔离。
- **验收口径**：越权调用在 API 层被拒绝；所有写操作都有确认与审计记录；脱敏测试无密钥泄漏。
- **落地记录（2026-11-20）**：新增 `core/ai_tools.py` 与 `ai_tool_audit` 表，提供 7 个白名单工具（项目/实验/指标/失败运行/成员查询与实验移动）。写操作必须先返回预览、二次确认后才执行；权限继承项目角色；设置页「AI 工具沙箱」可直接调试并查看最近调用审计。

## P1 · AI 科研纵深

> 这一组直接提升科研效率：帮用户想清楚、查清楚、写清楚，并在实验失败和运行异常时给出可执行建议。

### 39. 对话式需求澄清 Copilot

- **现状**：用户填一句创新点，系统直接生成方案；模糊想法经常产出空泛方案。
- **问题 / 机会**：科研想法往往需要 2–5 轮追问才能明确：研究问题、对象、数据、基线、指标、与已有工作的差异。
- **建议做法**：
  - 创建实验前增加「AI 问诊」：根据创新点自动提出 5 个关键问题。
  - 用户回答后生成结构化研究卡片：问题、假设、方法、数据、指标、风险。
  - 研究卡片可直接填入实验标题与创新点，并作为方案生成的约束。
  - 支持“跳过追问”，保留当前一键创建体验。
- **预期收益**：减少空泛方案，提高首次生成质量。
- **验收口径**：对比同一批创新点，使用问诊后的方案字段完整率明显提升；用户可在 3 分钟内完成问诊。

### 40. AI 文献与资料助理

- **现状**：系统能读取本地文稿抽取创新点，但没有文献理解、相关工作梳理和引用管理能力。
- **问题 / 机会**：用户经常需要在实验之外查论文、整理 related work、找 baseline 和数据集。
- **建议做法**：
  - 支持上传 PDF/Markdown，抽取：研究问题、方法、数据集、指标、结论、局限。
  - 生成「相关工作矩阵」：论文 × 方法 × 数据集 × 指标 × 与本项目的差异。
  - 对每条声称要求给出原文页码或段落定位，避免伪造引用。
  - 可把某篇论文中的 baseline 一键转成实验方案草稿。
  - 文献条目归属项目，纳入项目知识库和分享权限。
- **预期收益**：从“写实验”扩展到“读懂领域并设计实验”。
- **验收口径**：上传 10 篇论文，抽取字段准确率可人工核验；所有引用都能定位原文。

### 41. AI 实验设计助手

- **现状**：模板与批量实验可生成参数组合，但不判断哪些实验最值得做。
- **问题 / 机会**：科研时间有限，盲目消融和网格搜索会浪费 GPU/API 预算。
- **建议做法**：
  - 根据假设自动生成实验计划：主实验、必要条件、消融、敏感性分析、稳健性检查。
  - 对每个实验标注信息增益、成本估计和优先级。
  - 提供因子设计、正交表、随机种子重复、样本量/功效分析建议。
  - 预算紧张时推荐“最小可发表实验集”。
- **预期收益**：把“能跑很多实验”升级为“先跑最有说服力的实验”。
- **验收口径**：每个方案都带实验优先级表；用户可选择按预算生成不同档位计划。

### 42. AI 代码审稿与测试生成

- **现状**：代码由 LLM 生成，用户可改并保存；运行前没有系统性的静态审查。
- **问题 / 机会**：随机种子、数据泄漏、路径硬编码、指标计算错误等问题常常跑完才发现。
- **建议做法**：
  - 代码生成后自动执行轻量审查：随机种子、train/test 泄漏、硬编码路径、指标公式、异常吞掉、依赖缺失。
  - 自动生成 smoke test：用 toy data 跑 1 个 step，验证指标上报和保存逻辑。
  - 支持安全扫描结果二次确认后才允许推送 GitHub。
  - 审稿结果挂在 run 的代码快照上，随报告一起归档。
- **预期收益**：在运行前拦住低级错误，减少一次失败运行的时间与费用。
- **验收口径**：内置规则至少覆盖 10 类常见错误；smoke test 能在本地或目标主机沙箱中执行。

### 43. 失败自愈工单

- **现状**：失败时给出诊断卡与修复建议，用户需要手动改代码再跑。
- **问题 / 机会**：很多失败是依赖缺失、路径错误、OOM 参数过大等可模板化修复的问题。
- **建议做法**：
  - 诊断结果自动生成「修复工单」：错误签名、证据、建议补丁、影响文件、预计风险。
  - 用户点击「生成修复分支」后，AI 只创建代码快照 fork，不直接覆盖原实验。
  - 修复后可一键提交新 run，与原 run 建立父子关系。
  - 连续两次修复失败时，停止自动建议并提示人工介入。
- **预期收益**：从“告诉你哪里错了”走向“帮你准备一次安全重试”。
- **验收口径**：OOM、缺依赖、路径错误三类高频问题能生成可审阅补丁；所有修复都有 fork 记录。

### 44. 指标异常检测与早停建议

- **现状**：监控能采集指标并画图，但主要靠用户自己看曲线。
- **问题 / 机会**：loss 爆炸、指标长期平台、验证集反常波动、过拟合都可以通过轻量时序分析提前提示。
- **建议做法**：
  - 对每个指标维护滑动窗口，检测突增/突降、长期不增长、方差异常。
  - 结合判据与验证集指标给出早停建议，并说明触发依据。
  - 通知系统增加 `metric_anomaly` 事件，走同一套 Webhook 与免打扰规则。
  - 报告中自动附「稳定性摘要」：波动区间、异常点、是否建议增加 seed。
- **预期收益**：少看无效日志，少烧无效 GPU 时间。
- **验收口径**：构造异常指标序列能稳定触发；正常波动不产生大量误报。

### 45. 跨实验知识库问答

- **现状**：实验、报告、审计、项目都结构化存储，但用户只能搜索标题/标签/时间线。
- **问题 / 机会**：项目做久后会问“哪个实验试过这个 baseline？”“哪次 OOM 是怎么修的？”“某个结论有没有被复现？”
- **建议做法**：
  - 为实验建立轻量索引：标题、创新点、方案、代码摘要、结论、指标、失败诊断、审计。
  - 支持自然语言问答，答案必须引用实验 ID、run ID、报告段落。
  - 支持项目范围与全局范围切换，严格继承项目角色权限。
  - 用户可把问答结果保存为项目笔记。
- **预期收益**：把历史实验变成可查询的科研记忆。
- **验收口径**：10 个典型问题能在对应项目中找到正确实验；越权查询返回无权限或过滤结果。

### 46. 报告写作与审稿一体化

- **现状**：报告可导出 Markdown/Word/PDF，AI 自审单独展示；写作仍需用户自己组织。
- **问题 / 机会**：从结论到论文段落之间还有一步“科研叙事”，AI 可以辅助但不能虚构。
- **建议做法**：
  - 基于已核验数字生成 Results 草稿、Limitations 草稿、Related Work 骨架。
  - 生成「主张—证据表」：每句主张后挂 metric/log/commit。
  - 模拟审稿后生成 rebuttal 提纲：针对每个 major issue 给出回应和需补实验。
  - 导出时让用户选择“保守模式/论文草稿模式”，前者只允许已验证表述。
- **预期收益**：报告从“实验记录”进一步接近“可投稿初稿”。
- **验收口径**：草稿中每个数值都能回溯；保守模式下无证据主张不输出为结论。

### 47. 成本路由与预算助手

- **现状**：系统记录 LLM token，支持 fallback，但用户不能主动选择成本/质量策略。
- **问题 / 机会**：不同阶段适合不同模型：抽取可用便宜模型，审稿/报告适合强模型。
- **建议做法**：
  - 设置页增加 AI 策略：经济 / 均衡 / 高质量。
  - 按任务类型配置模型：抽取、方案、代码、总结、审稿、诊断。
  - 创建实验前预估 token 成本，运行前提示本次操作预计花费。
  - 设置月度/项目级预算，超限后降级模型或要求确认。
  - 报告中记录 AI 成本，作为实验复现成本的一部分。
- **预期收益**：AI 成本可见、可控、可优化。
- **验收口径**：不同策略下同一任务质量差异可评测；预算超限行为符合用户设置。

## P2 · AI 协作与生态

> 这一组面向团队和长期生态，优先级低于科研纵深，但能显著提升“课题组工作台”的想象力。

### 48. 多模态实验理解

- **现状**：系统理解文本、日志和指标，对图片/图表/截图没有专门能力。
- **问题 / 机会**：科研中经常需要看 loss 曲线、注意力图、医学影像、错误截图；这些信息目前要用户自己描述给 AI。
- **建议做法**：
  - 支持上传截图或曲线图，AI 描述异常点、趋势和与指标的关系。
  - 观察页允许访客对图表批注，AI 汇总成「外部反馈摘要」。
  - 多模态理解结果同样绑定证据：原图区域、指标点、日志时间。
- **预期收益**：AI 能看懂用户看到的东西，而不是只读文本。
- **验收口径**：至少支持 PNG/JPG 曲线图和简单实验结果图；所有描述不可当成实测结论。

### 49. 项目周报与协作摘要

- **现状**：全局时间线记录了事件，但信息是流水账。
- **问题 / 机会**：课题组长需要知道“这周做了什么、什么卡住、下周做什么”。
- **建议做法**：
  - 每周自动生成项目摘要：新增实验、完成运行、失败原因、判据状态、成员贡献。
  - 识别阻塞项：连续失败、无指标、长时间无更新、待确认 checkpoint。
  - 生成组会 Markdown 或 Webhook 消息。
  - 摘要只基于项目内可见数据，严格继承角色权限。
- **预期收益**：项目状态不用人工整理，协作更透明。
- **验收口径**：摘要中每条事件可点回实验；viewer 只能看到其权限范围内的摘要。

### 50. 科研画像与方法推荐

- **现状**：个人主页记录研究方向、技能与经历，但没有和实验行为联动。
- **问题 / 机会**：长期使用后，系统其实知道用户擅长什么、常用什么方法、哪些实验总失败。
- **建议做法**：
  - 根据个人档案与历史实验生成科研画像：方法偏好、数据领域、常用指标、失败模式。
  - 推荐下一步方法：是否该加基线、做消融、增加 seed、换统计检验。
  - 推荐可复用模板或垂直实验包。
  - 画像仅本人可见，不进入项目分享链接。
- **预期收益**：工具用得越久，越懂用户的研究风格。
- **验收口径**：推荐可解释，必须说明依据来自哪些历史实验；用户可关闭画像学习。

### 51. AI 插件与模板工坊

- **现状**：实验模板固定在代码中，AI 调用层也相对固定。
- **问题 / 机会**：不同学科需要不同方法包；高级用户希望自定义 prompt、工具和评测规则。
- **建议做法**：
  - 允许项目 owner 创建项目级 AI 模板：prompt 片段、字段约束、默认判据、报告结构。
  - 插件以声明式配置描述：需要的工具、输入字段、输出字段、权限要求。
  - 提供官方模板市场：医学影像、NLP 评测、强化学习、统计模拟等。
  - 所有第三方插件默认只读，写操作需管理员启用并审计。
- **预期收益**：从单一产品扩展为可生长的科研 AI 工作台。
- **验收口径**：普通用户能导入模板；owner 能管理项目模板；插件越权调用被拒绝。

## 实施原则

1. **证据优先**：AI 输出必须尽量绑定 metric、log、commit、报告段落或原文页码。
2. **人在环**：写操作默认只生成补丁/草稿，不自动覆盖用户数据；高风险操作必须确认。
3. **角色继承**：所有 AI 查询和工具调用继承项目角色，viewer 不能借助 AI 越权读取。
4. **可关闭**：用户可以选择关闭画像学习、外部知识检索或自动工具调用。
5. **可评测**：每个 AI 功能都要有评测样本和回归指标，不用“感觉不错”作为验收标准。
6. **成本可见**：AI 调用要有任务类型、模型、token 和费用摘要，避免隐性成本。
7. **隐私边界**：上传文献、代码和日志前明确提示脱敏；分享链接中的 AI 回答必须遵守脱敏设置。
8. **不要伪造**：引用、数字、显著性、论文表述必须区分“已验证”和“建议”，宁可少写，不可编造。
